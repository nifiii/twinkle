## 3. 方案

### 3.1 调用与数据流

沿用现有服务边界：

`现有页面/API → 既有任务和服务 → 文本/视觉配置选择 + 显式思考参数 → 方舟Chat或Responses → 现有业务校验 → 现有持久化与展示`

| 入口/模块（基于e1e2155） | 当前行为 | 目标行为 |
| --- | --- | --- |
| `services/doubaoService.ts` | 单个getDoubaoClient将纯文本与封面/扫描PDF都绑定ARK_MODEL_ID | 在现有小型工厂中明确文本/视觉用途，视觉处理优先读取ARK_VISION_MODEL_ID，缺失时继续按原约定回退文本配置；不新增多层适配框架。 |
| `routes/analyze.ts` | Responses使用ARK_VISION_MODEL_ID，否则固定旧Lite；未指定思考档位 | 保留独立入口与OCR契约，更新Lite默认版本，显式关闭思考。 |
| 教材学习、课件任务、英语听力、错题讲解和原创试卷服务 | 各自创建Chat客户端并读取ARK_MODEL_ID | 固定版本配置生效，显式低强度思考；保留提示词、输出结构和任务流程。 |
| `routes/assessment.ts`、`routes/wrongProblems.ts`等仍可调用的历史入口 | 使用同一文本配置 | 纳入调用清单与兼容检查，不漏改仍可调用的文本请求。 |
| `services/gradingService.ts` | 存在历史调用代码 | 不恢复入口或启用相关开关；静态核对业务不可达及现有禁批改验收。 |
| `.env`与`.env.example` | 实际配置与示例存在，示例视觉回退说明与analyze默认不一致 | 修改前备份实际配置，示例准确记录用途、固定版本、回退和部署覆盖规则；不提交密钥。 |

### 3.2 API、数据、UI契约

- 前端API路径、请求字段、响应字段、错误码、ownerId语义保持既有契约。
- 无表结构、历史数据迁移或新存储字段；历史任务继续可访问。
- UI flow、页面状态、UI/UX design system与frontend design：本轮无新增页面或交互，以既有已确认设计为准；验收已有生成进度、成功、失败和作答回顾状态。
- 模型响应格式支持不等于业务合格；原校验继续生效。原本返回JSON数组的接口不直接强套json_object；不要静默改返回对象形状。
- 真实探测只使用人工构造的短文本与合成图片，不默认把整本教材或历史学生数据发给模型。

### 4.1 影响面与根因说明

- 已用GitNexus绑定`answer-review`工作树并对关键符号运行query/context/impact，调用图结果存在FTS部分失败和旧元数据缺失，impact返回UNKNOWN；不将零解析调用者解释为安全。

- 备选解释如“API Key没有新模型权限”“当前ep实际已升级”尚未通过推理或接入点详情验证，不作为已确认故障。

### 4.2 费用、性能与版本风险

- 旧2.0 Pro在输入不超过32k token时，公开常规单价为输入3.2、输出16元/百万token；新2.1 Pro为6、30元，同等未缓存token数约增加87.5%。该比较不能用于未知底层模型的当前文本ep，也不能直接推导每次任务总费用。
- 输入大于32k的旧档位、缓存命中、思考token和不同推理方式需另算；不能承诺固定账单。
- 当前最新Pro不是最低费用选择。若选择Lite承担图片识别，费用较低，但相对现有Pro属于档位变化，必须另行确认，不能作为隐式“优化”。
- 固定260915版本避免Evolving周级迭代带来未验收行为变化；不做自动追随新型号。
- 新模型默认high思考可能增加耗时；保持现有服务预算并真实测量，不以抬高超时掩盖兼容问题。
