# 性能与 Gemini 清理 PRD

状态：Gate 2 已确认

## 1. 背景

当前图书处理、OCR 与课件生成均直接竞争豆包模型和单容器资源，但没有跨流程的全局调度。已存在的局部并发又会叠加：文本版 PDF Markdown 转换最多 6 个模型请求并发，扫描版 PDF OCR 最多 3 批并发，课件请求一次生成 5-8 个长内容节。前端试卷录入仍调用完整 OCR+结构化分析路径，未使用已存在的两阶段 API。

Gemini 清理不是删除无用包：图书元数据服务、历史类型/UI 标识以及 LiveTutor 仍有实际依赖。LiveTutor 当前从浏览器直接使用 Gemini API Key，存在密钥暴露风险，且协议与现有豆包文本、OCR、TTS API 不等价。

## 2. 目标

- 在 3 个资源密集任务并发运行时，满足 `BR-001` 至 `BR-003` 的 P95 端到端时延。
- 最多接收 10 个资源密集任务，超出 3 个运行槽位时前端可见排队状态。
- 移除所有 Gemini 依赖并迁移 LiveTutor 至豆包实时双向语音服务，满足 `BR-005`、`BR-007`、`BR-008`。
- 以结构化阶段耗时和固定样本基准证明优化结果，而不是仅以主观等待感受判断。

## 3. 方案

### 3.1 MVP 范围

| 编号 | 范围 | 用户可见结果 |
| --- | --- | --- |
| M-001 | 统一任务调度与状态模型 | OCR、图书处理、课件生成进入同一队列；第 4 至第 10 个任务显示排队位置或状态。 |
| M-002 | 阶段耗时与基准测试 | 页面和日志可区分上传、排队、PDF 文本提取、图片转换、模型调用、保存、首屏结果等阶段；固定样本可自动复测。 |
| M-003 | PDF 处理路径优化 | 避免重复封面转换；按 PDF 类型选择文本/扫描路径；全本转换纳入任务队列与资源预算。 |
| M-004 | OCR 路径收敛 | 选择账户内低延迟视觉模型并控制输出预算；OCR-only 与结构化分析可作为内部两阶段优化，但用户完成态必须是结构化题目可保存；取消完整 OCR 路径与分阶段 API 并存却未使用的状态。 |
| M-005 | 课件生成预算 | 将输出体积、模型选择、请求超时和任务调度纳入全局预算，确保 60 秒目标优先于非必要长输出。 |
| M-006 | Gemini 清理与 LiveTutor 迁移 | 元数据统一走豆包；删除 Google SDK、密钥、调用、类型值和 UI 标识；LiveTutor 改为浏览器至本服务再至豆包的实时语音会话。 |

### 3.2 非范围

- 不承诺 3 并发以上仍满足 60/60/180 秒；第 4 至第 10 个任务使用排队策略。
- 不改变教材、OCR 或课件的业务内容标准，除非基准验证证明当前冗余输出无法满足时延目标并获得新的范围确认。
- 不进行 SQLite 替换、前端框架重写或无关 UI 重设计。
- 不在未经验证前假定豆包实时语音的协议、编码或限流与 Gemini 相同。

### 3.4 成功与发布标准

- 固定 OCR 样本、指定 PDF 样本和课件场景分别在 3 并发下运行 5 次，P95 达到 `60 秒 / 180 秒 / 60 秒`。
- 10 个任务提交时，系统最多启动 3 个资源密集任务，其余任务具有可见队列状态，且任务不丢失。
- 仓库、构建产物和运行时环境不再包含 Gemini SDK、密钥或调用；LiveTutor 功能与 3 秒首段语音 P95 通过独立测试。
- 发布具备阶段级日志、仪表盘指标、灰度开关和可回退版本。

## 4. 风险

- 56.9 MB PDF 的上传时长取决于用户网络；服务端优化不能替代带宽容量。验收必须记录客户端上传阶段，避免把网络延迟误归因到解析。
- 现有单容器架构在 3 个全本扫描 PDF 同时转图时可能受 CPU、磁盘和内存限制；需要先基准化，再决定是否需要单独 worker。
- 豆包实时音频的实际接入参数、区域、额度和成本必须以发布时官方文档与账户开通状态为准。
- 删除历史 Gemini 路径可能影响旧 `extractionMethod` 数据展示，需向后兼容已有记录而非迁移时删除数据。

## 5. 回滚

- 调度、PDF 路径和模型选择均使用独立配置开关，发布异常可回退到上一容器镜像。
- LiveTutor 在新豆包实时会话完成端到端验证前不删除现有部署版本；新版本不得继续向浏览器注入 Gemini 密钥。
- 任务状态变更采用向后兼容字段，避免回滚后旧版本无法读取排队或处理中任务。

## 6. FAQ

### 为什么不单纯提高模型调用并发？

现有每个 PDF 已可发出 3 或 6 个模型请求。多个用户同时操作时会叠加并发并触发上游限流、重试和资源争用，端到端耗时反而变长。

### 为什么 PDF 的“可用”不等于元数据已返回？

当前前端会在元数据解析后让用户确认，再由后台转换 Markdown。用户最终可读、可用于后续学习流程的状态取决于后台任务完成，因此 SLO 必须覆盖完整状态转换并通过阶段指标拆分归因。
