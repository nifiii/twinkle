状态：T-001 已完成，性能门禁未通过

## 1. 背景

## 2. 目标

建立后续实现和发布必须使用的阶段基线，并确认是否可以仅通过任务队列和并发槽位满足以下已确认目标：OCR <= 60 秒、PDF <= 180 秒、课件 <= 60 秒，均以 3 并发、5 次运行的最慢值为门禁。

## 3. 方案

PDF 的运行时曾返回 `pageCount=1`，而本地无网络基线已确认该样本实际为 50 页。T-005 已改为使用 `parsePDF().pageCount`，隔离 Job 实测返回 50 页；该缺陷不会再误导页面显示或阶段决策。

### 3.2 根因确认

OCR 没有排队、重试或 JSON 解析失败。服务端一次模型调用耗时占端到端的 99.5%，且生成了 11,704 输出 tokens。结论：调度器、增加模型槽位、前端轮询或上传优化均无法把该路径降至 60 秒。

PDF 的主要耗时同样来自元数据视觉分析及两个 Markdown 模型分片；当前两个分片并行执行，单任务仍有约 37 秒余量。三并发时若不控制上游请求，模型调用会叠加；若槽位过低，PDF 排队会消耗这部分余量，因此不能在单任务数据上随意设置全局槽位数。

### 3.4 T-001A 视觉模型探测

当前 Pro 路径的 222 秒 OCR 调用无法通过目标。账户模型列表中的两个旧视觉候选在 Responses 端点均返回无访问权限；`doubao-seed-2-0-mini-260428` 在 4,000 token 下约 53 秒但只返回 8 题，5,000 token 下超过 100 秒；因此两者均被拒绝。

通过组合是 `doubao-seed-2-0-lite-260428`，使用紧凑结构化合同和 `max_output_tokens=3000`。每个结果均含 9 题以及题号、自包含题干、学生答案、标准答案、批注、知识点和状态。

| 并发 | 耗时 | 输出 tokens | 结构校验 |
| ---: | ---: | ---: | --- |
| 1 | 38.273 秒 | 2,273 | 通过 |
| 3 - 任务 1 | 45.592 秒 | 2,086 | 通过 |
| 3 - 任务 2 | 50.156 秒 | 2,450 | 通过 |
| 3 - 任务 3 | 56.713 秒 | 2,858 | 通过 |

结论：OCR 的初始视觉模型配置应为 `doubao-seed-2-0-lite-260428`、最大输出 3,000 tokens、视觉模型槽位 3。56.713 秒仅为探测 API 的最慢值，T-004 完整 Job 链路必须再执行 3 并发 x 5 次门禁，证明包含提交、排队、持久化和页面状态后仍不超过 60 秒。

## 5. 回滚

基准环境不改变生产数据或容器。运行时容器使用命名项目 `twinkle-benchmark` 和独立数据卷；测试结束后执行 `docker compose ... down --volumes`。基准脚本的 MIME 修正仅使测试请求符合现有服务端白名单，不影响生产 API 规则。

## 6. FAQ

### 为什么没有执行 3 并发 x 5 次？

OCR 在单任务已超标 163 秒。继续执行 15 次已知失败的调用只会增加账户成本，不会改变“当前模型路径无法达标”的结论。

### 能否直接把 OCR 模型并发调到 3？

不能。当前单次调用本身为 222 秒；并发只会增加上游配额争用，不能把单次生成压缩到 60 秒。

### 下一步为什么需要范围确认？

已确认的 T-004 只允许迁移执行方式并保持当前结构化输出，不包含更换视觉模型或收紧输出预算。实测证明这两类改变至少需要其一，因此属于范围扩展，必须由用户明确确认后再实施。
