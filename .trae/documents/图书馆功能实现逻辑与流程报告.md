## **图书馆全本 Markdown 转换修复方案 (基于豆包官方文档)**

经过对火山引擎（Ark）官方文档的深度核查，确认了“转换不全”的根因：**默认输出 Token 限制**。以下是基于官方接口规范的重构方案：

### **1. 问题根因定位**

* **输出限制**：豆包 API 在未指定参数时，默认输出长度通常限制在 **4096 Token**（约 8000 汉字）。即便输入了 10 万字，AI 也会在写满 4096 Token 后强行收尾。
* **模型潜力**：官方文档显示 `doubao-seed-1.8` 模型支持高达 **256k** 的上下文窗口和 **64k** 的单次回答 Token。这意味着单次请求理论上可以生成约 10-15 万字的 Markdown 内容。
* **代码遗漏**：当前 `doubaoService.ts` 调用时未设置 `max_tokens` 参数，导致使用了极小的默认值。

***

### **2. 基于官方接口的重构方案**

#### **方案 A：解锁模型上限 (首选方案)**
我们将利用豆包长文本模型的能力，通过调整接口参数直接获取完整转换：
* **取消截断**：将输入限制从 10 万字符提升至 20 万（约 256k Token 的安全线）。
* **指定 `max_tokens`**：在 API 请求中显式指定 `max_tokens: 64000`。这将允许 AI 输出比现在长 16 倍的内容，足以涵盖绝大多数单本教材。

#### **方案 B：流式/分段请求 (大文件兜底)**
针对超过 64k Token 的超长教材，采用官方推荐的 **分段合并逻辑**：
* 逻辑：如果文档字符数 > 15 万，自动切换为分段模式，每 10 万字作为一个 Block 进行转换，最后进行物理合并。

***

### **3. 实施步骤**

1. **更新 `doubaoService.ts`**：
   * 在 `chat.completions.create` 中增加 `max_tokens: 64000`（或模型支持的最大值）。
   * 调优 `SYSTEM_PROMPT`，明确要求“即使内容很长也要完整转换，不要缩减”。
2. **优化后端解析**：
   * 确保 `pdf-parse` 提取的全文能完整传递给转换函数。
3. **性能测试**：
   * 使用 50 页以上的 PDF 进行测试，确认生成的 Markdown 文件大小从 15K 提升到正常水平（通常为数百 K）。

**通过此方案，我们将利用豆包模型原生的长文本生成能力，解决转换中断的问题，实现与豆包 APP 一致的完整转换体验。请确认执行。**
