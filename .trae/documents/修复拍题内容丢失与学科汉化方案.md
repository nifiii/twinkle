# 架构级修复：拍题数据一致性与学科汉化方案

## 1. 结构化数据一致性架构说明

作为一个架构师，我需要向您说明当前系统的存储设计逻辑：

*   **双重存储策略**：系统同时保存了 **非结构化 Markdown (Obsidian)** 和 **结构化 JSON (SQLite)**。
    *   **Markdown 文件**：存储在磁盘上，用于长期归档、全文展示及跨平台同步（Obsidian 兼容）。
    *   **SQLite `problemsJson`**：这是为了高性能 UI 渲染而设计的“结构化缓存”。它将题目、学生答案、标准答案等字段预先解析，使得前端能够直接渲染交互式的题目列表，而无需在浏览器中进行复杂的 Markdown 解析。
*   **当前失效原因**：
    1.  **详情加载缺失**：目前的详情弹窗直接使用了列表接口的数据快照。而列表接口出于性能考虑，排除了大体积的 Markdown 内容和详细题目 JSON。
    2.  **状态映射错误**：前端加载时将 `problems` 字段强制置空，导致即使后端有数据，前端也无法显示。

## 2. 核心技术修复路线

### A. 数据链路闭环 (后端)
*   **scannedItems.ts (详情路由)**：修复 `GET /api/scanned-items/:id` 接口，确保其在返回响应时，同时读取并合并：
    1.  来自磁盘文件的 **Markdown 原文**。
    2.  来自数据库表的 **`problemsJson` 结构化数据**。
*   **fileStorage.ts (存储逻辑)**：验证文件保存路径索引的正确性，确保数据库记录的 `mdPath` 能准确指向持久存储目录。

### B. 详情按需加载 (前端)
*   **KnowledgeHub.tsx (交互重构)**：
    *   在打开详情弹窗时，如果当前数据是不完整的（缺失 Markdown 或题目列表），立即触发 `fetchScannedItemById`。
    *   通过完整的详情响应，同时填充“原始试卷（Markdown）”和“结构化内容（JSON 渲染）”两个标签页。

### C. 学科名称规范化 (全链路)
*   **映射机制**：引入 `SubjectMapper` 工具，将 AI 识别出的 `English` 等英文名，在数据入库和前端展示时统一映射为 `英语` 等中文规范名称。
*   **UI 适配**：同步更新侧边栏、筛选器及卡片标签，确保全局语言环境一致。

## 3. 部署稳定性增强
*   **持久化验证 (deploy.sh)**：确认 `/opt/hl-os/data` 挂载点在部署重启过程中的稳定性，防止因容器或进程重启导致的文件系统访问异常。
